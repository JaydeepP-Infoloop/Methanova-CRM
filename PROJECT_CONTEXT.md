# PROJECT_CONTEXT.md — Methanova CRM

This is the living, canonical reference for this codebase. **Re-read this file before starting any new feature.** Update it whenever a schema, role, or workflow decision changes — it must never go stale. If code and this document disagree, treat that as a bug: either the code drifted or the document needs updating, and either way stop and reconcile before building on top of it.

This file governs *what* the system does and what phase work belongs to. Its companion [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md) governs *how the UI looks and behaves* — design tokens, component plan, per-page layouts, and the D1/D2/D3 redesign phasing. Read that one before writing any UI.

## Current status — read this before assuming anything is built

**Done: the auth/RBAC/app-shell foundation.** This is the "Day 1" skeleton every business module renders inside — login, session handling, role-gated navigation, and one landing page — and nothing more. Concretely:

- **Backend**: `apps/api/src/db/connection.ts` connects to the MongoDB replica set from `MONGODB_URI`. The seed script (`apps/api/src/db/seed/index.ts`) creates the eight `RoleRecord`s, the counters, default GST master data, and exactly one admin (`Role.DIRECTOR`) user — see "Environment variables" below for how its credentials are supplied. Auth (`apps/api/src/core/auth/`) implements `POST /auth/login`, `GET /auth/me`, `POST /auth/logout`, and `POST /auth/refresh`, using a short-lived JWT access token plus a rotating opaque refresh token (hashed, stored in a `refresh_tokens` collection, delivered as an httpOnly cookie scoped to `/auth`). `apps/api/src/middlewares/index.ts` provides `requireAuth`, `requirePermission(module, level)`, `requireRole(...roles)`, a `morgan`-based `requestLogger`, and the global `errorHandler`; `GET /health` is a plain liveness check.
- **Frontend**: `apps/web/src/app/providers.tsx` defines an `AuthContext` (`user`, `isAuthenticated`, `isLoading`, `login()`, `logout()`) as plain React state — deliberately **not** TanStack Query cache state, because `removeQueries`/`setQueryData(key, undefined)` on an already-fetched query observer do not reliably force a synchronous re-render in this version of `@tanstack/react-query` (confirmed by hands-on debugging: a manual `navigate()` after `logout()` raced a stale `isAuthenticated` read in `Login`, and even after removing that race, cache-based clearing left the shell rendered). `QueryClientProvider` still wraps the whole app for every other module's data fetching. `apps/web/src/app/router.tsx` mounts `Login` at `/login` and everything else under `/app`, gated by `ProtectedRoute` (`apps/web/src/app/layout/ProtectedRoute.tsx`). `AppShell` (`Sidebar` + `Topbar`) renders the nav in `apps/web/src/app/nav.tsx`, filtered so a section shows only if the current role has at least READ on one of its modules. `Dashboard` (`apps/web/src/modules/reports/pages/Dashboard.tsx`) is the `/app` index route — a CRM strip wired to live `GET /api/crm/leads/summary` and `GET /api/crm/my-day` overdue counts for roles with `crm:READ`; billing, compliance and active-projects panels stay honest empty states until those modules exist. The read-only Users list (`apps/web/src/modules/admin/pages/UserPage.tsx`) already existed from the earlier scaffolding pass and satisfies this requirement as-is.
- **Verified live**: seed → login → `/auth/me` → refresh (rotates the cookie) → logout (revokes it) → RBAC-gated `GET /api/admin/users`, all exercised against a real MongoDB replica set, plus the full browser flow (login → `/app` dashboard → Users list → logout → back to `/login` → re-login) in a running dev server.

**Done: the CRM lead inbox & intake.** This is the first real business feature in the system — see [MODULE_MAP.md](./MODULE_MAP.md) for the per-feature checklist. Concretely what is now real:

- **The Lead entity was rebuilt.** The original scaffold (`organisationName`, one `contactName`, a defaulted stage) is gone. A lead now carries `companyName`, optional `entityType`, format-validated `gstin`/`pan`/`cin`, an embedded `contacts[]` array (exactly one primary, enforced server-side), geography references (`stateId`/`districtId`/`talukaId` required, `villageId` optional — each validated as actually belonging to its stated parent), optional registered/site addresses, `leadSourceId` with conditionally-required `sourceDetail`, `feedstockTypeIds[]`, `feedstockQtyTpd`, optional `feedstockTieupStatus`, a server-computed `expectedCbgTpd`, and a required `nextAction`/`nextActionDate`. System-set on creation and never accepted from the client: `leadCode` (atomic counter, prefix from `LEAD_CODE_PREFIX`), `stage` (`NEW_LEAD_STAGE`), `stageSince`, `temperature` (Cold), `ownerUserId` (null — leads land unassigned), `firstResponseAt` (null).
- **New master collections**, seeded with a minimal real slice of Gujarat: `geo_states`, `geo_districts`, `geo_talukas`, `geo_villages`, `lead_sources`, `feedstock_types` (with configurable `yieldFactor`; a null factor means "not configured" and the UI must show an em dash rather than a wrong number). Read endpoints live under `GET /api/masters/*`.
- **Lead endpoints**: list with server-side pagination, text search over company name and lead code, filters (stage, owner, source, district, temperature, plus unassigned / no-first-response / overdue-next-action), sorting defaulting to longest-waiting-first; `GET /crm/leads/summary` returning the two counts **derived at query time**, never stored; `GET /crm/leads/duplicates` for the intake form's non-blocking warning; `POST /crm/leads/expected-cbg` for the live estimate.
- **Lead Inbox UI** (`modules/crm/pages/LeadPage.tsx`) with two clickable stat cards that toggle their filters, the SLA-breach flag (threshold from `LEAD_FIRST_RESPONSE_SLA_DAYS`), overdue next-action dates in the danger colour, and an empty state that offers the Add Lead action. **Add Lead wizard** (`modules/crm/components/AddLeadWizard.tsx`) as a three-step modal. A **read-only lead detail placeholder** exists at `/app/crm/leads/:id` purely so inbox rows have somewhere to land.
- **Three new shared primitives** — `Modal`, `Stepper`, `Toast` — documented in DESIGN_SYSTEM.md §3.
- **Validation errors are now HTTP 400 with a `fieldErrors` map**, not 500 with a stringified Zod blob. `apiClient` throws `ApiError` carrying the parsed body so the wizard can route each message to the step that owns the field.

**Done: the lead detail workspace, assignment, and the activity log.** The second real business feature — what turns a lead from something you can create into something you can work.

- **Assignment**: `POST /api/crm/leads/:id/assign` sets `ownerUserId` (omitting `userId` means "assign to me"). Both the previous and new owner are written to the polymorphic `audit_logs` collection, so **reassignment history is queryable without a new collection**.
- **Activities rebuilt** from the four-field scaffold into a polymorphic log: `parentType` (`LEAD` now, `PROJECT` later) + `parentId`, eight `type` values, `occurredAt`, a per-parent `sequenceNo` allocated from the atomic counters service (so "the third follow-up" survives), `internalParticipantIds`, `externalContactNames`, required `summary`, `outcome`, and `nextFollowUpDate`/`nextFollowUpAction`. Two optional structured sub-documents — `plantVisit` and `siteVisit` — are accepted only for their own type and rejected outright on any other. **The `siteVisit` record is the intended seed for the Module B feasibility survey** (noted in the model).
- **`POST /api/crm/leads/:id/activities` is transactional.** In one replica-set transaction it creates the activity, stamps `firstResponseAt` on the parent lead when it is null *and the type is anything other than `NOTE`* (a note is internal record-keeping, not contact with the client), and carries the submitted follow-up onto the lead's `nextAction`/`nextActionDate` — so the commitment lives where the inbox, and later My Day, reads it. If any part failed, none of it would apply and the inbox would not disagree with the timeline.
- **Lead detail workspace** replaces the placeholder: header band (code, company, stage, temperature, owner or "Unassigned", days in stage), a **read-only** eight-stage rail rendered with `Stepper`, an activity timeline (newest first, sequence number, type icon, who was spoken to, summary, outcome, committed follow-up), and a right rail of snapshot / read-only contacts / next action with overdue dates in the danger colour.
- **Inbox row actions**: "Assign to me" and "Log first response" both refetch the list and the two summary counts, so the Unassigned and No-first-response cards update without a reload.
- **New endpoint `GET /api/masters/users`** — a minimal colleague list for the owner and participant pickers, gated at `crm/READ`. `GET /api/admin/users` could not serve this: it is gated at `admin/READ`, which only the Director holds, so a Sales Head assigning a lead would be refused.

**Done: qualification scoring and stage transitions.**

- **Qualification criteria are master data**, not code: a `qualification_criteria` collection seeded with the three dimensions §2 names (feedstock availability, site viability, budget & finance) at equal weight. Weights and the recommend-threshold are commercial judgement that will be calibrated against real outcomes, so they are rows to edit rather than constants to redeploy. `GET /api/masters/qualification-criteria` serves them.
- **`POST /api/crm/leads/:id/qualify`** records per-criterion scores (0–5, where 0 means "not assessed"), computes the weighted percentage **server-side**, and moves the lead in the same transaction — `QUALIFIED` → `QUALIFICATION`, `DISQUALIFIED` → `LOST` with a mandatory reason. Both routes still go through `assertTransition`, so qualification is not a licence to make an illegal jump. **Criteria left unscored are excluded from both sides of the ratio rather than counted as zero**, so an unassessed dimension does not make a good lead look bad.
- **`computeQualificationScore` lives in `packages/shared-types`** and is used by both sides: the modal's live preview is the same function the server stores with, so the number a user sees while scoring cannot disagree with the number that gets saved.
- **The threshold produces a recommendation, never a verdict.** The modal shows "above/below threshold"; a human still presses Qualify or Disqualify. It is stored in `master_data` under `qualification-settings` and edited from the admin screen, not compiled in.
- **Criteria admin screen** at `/app/admin/qualification-criteria`: add, retune and soft-delete criteria, and set the recommend-threshold. It shows each criterion's **live share of the score** as weights are edited, because a raw weight of "2" means nothing on its own. A criterion's `key` is immutable once created — recorded lead scores reference it, and renaming would orphan them. Changing weights never rewrites scores already recorded: a historical score reflects the rubric it was decided under.
- **Reads and writes on this reference data are gated differently.** `GET /api/masters/*` stays at `crm/READ` because the qualify modal needs it; the criteria/settings write routes additionally require `admin/WRITE`, so a Sales Head can score a lead but cannot retune the rubric everyone is measured by. Verified: that role gets 200 on the read and 403 on both writes.
- **Stage transitions from the detail page**: the stage rail now offers exactly the legal targets from `TRANSITION_MAP` (`Stepper` gained a `clickableSteps` prop for this — without it, it stays a backwards-only wizard). Each move goes through a confirmation with an optional note, and `POST /:id/transition` now accepts a `reason` which is **required when moving to LOST** and persisted to `lead.lostReason` as well as the audit trail, because "why did we lose this" should not require querying `audit_logs`.

**Done: the geography and lead-source admin screens.** The intake form's two remaining seed-only reference sets are now editable by the Director.

- **One admin router, `POST/PATCH/DELETE /api/admin/reference/*`**, gated at `admin/WRITE` — deliberately separate from the `crm/READ` read routes under `/api/masters/*`, so everyone who fills in the intake form can resolve these lists but only an admin can change them. Verified: a Sales Head gets 200 on the read and 403 on both writes.
- **Geography admin** at `/app/admin/geography`: a four-column state → district → taluka → village drill-down that mirrors the cascade the intake form walks. Adding, renaming and removing happen in place. Uniqueness is scoped to the parent, so two districts named "Pune" can exist under different states but not under the same one.
- **Removal is refused while anything still points at a row**, and the server's message says exactly what is in the way ("Remove its 10 districts first", "1 lead uses this village"). The confirm dialog surfaces that message verbatim rather than a generic failure, because the count is the whole answer to "why not". Soft delete only (hard rule #6), so leads that already reference a removed row keep resolving.
- **Lead sources admin** at `/app/admin/lead-sources`: label, the detail field's label and placeholder, `detailRequired`, and sort order. The `key` is immutable once created — leads reference it.
- **`detailRequired` is now read from the row, not from a hardcoded key list.** `leads.service.ts` previously ORed the row's flag with a constant list of keys, which meant switching the toggle off in the admin screen would have been silently overridden and the server would have disagreed with the wizard. The row is authoritative on both sides. Verified end to end: unticking it in the UI makes a TENDER lead without a detail succeed, re-ticking it makes the same request 400 again.

**Done: the feedstock yield-factor admin screen.** The last seed-only master is now editable, and with it the one piece of reference data whose edits have a visible effect on records that already exist.

- **Screen** at `/app/admin/feedstock-types`: label, yield factor, unit and sort order per type, plus the number of leads listing each one. Same `admin/WRITE` gate and same referential guard as the rest — a type cannot be removed while any lead lists it ("2 leads list this feedstock"). Verified: a Sales Head gets 200 reading `/api/masters/feedstock-types` and 403 on the writes, the usage read and the recalculation.
- **`yieldFactor: null` is not `yieldFactor: 0`, and the UI keeps them apart.** Null means "not decided yet" — the type contributes nothing and the intake form names it back to the user instead of quietly understating the estimate. Zero is an assertion that this feedstock yields nothing. An empty input is null, a typed `0` is zero, and the row shows a "Not configured" pill for the former. The Zod schema is `z.number().min(0).nullable()` so the distinction survives the API.
- **Changing a factor does not rewrite leads that already exist**, because `expectedCbgTpd` is computed and stored at intake. That is the right default — silently rewriting business records is worse than showing an old number — but it leaves the CRM quoting assumptions nobody believes, so the screen counts the **open leads whose stored estimate no longer matches the current factors** and offers one explicit "Recalculate N leads" action.
- **The recalculation only touches open leads**, in one replica-set transaction, saving each lead individually so the audit plugin records a per-lead before/after under `lead_expected_cbg_recalculated`. Terminal stages are derived from `TRANSITION_MAP` rather than hardcoding WON and LOST: a won lead's estimate fed the MOU and the project that followed it, and a lost lead is history — neither should move because an engineering assumption was revised afterwards. Verified end to end: bumping cattle dung 0.03 → 0.1 left an open lead at 8, the recalculation moved it to 15, and a LOST lead stayed at 10 throughout.
- **The arithmetic lives in one place.** `expectedCbgFromFactors` was extracted out of `computeExpectedCbg` in `leads.service.ts` so the batch recalculation works from one in-memory factor map instead of re-querying per lead, and cannot drift from what intake stores.

**Done: contact editing and the two lead exits (park and mark dead).** What lets a lead leave the pipeline — temporarily or permanently — and lets the people on it be corrected.

- **`PATCH /api/crm/leads/:id/contacts` replaces the whole array**, not a single row. "Exactly one primary" is a property of the collection, so a per-contact endpoint would have to read the siblings anyway; sending the finished array is both simpler and the only shape the rule can be validated against. The before and after arrays both go to `audit_logs` — "who was the primary contact in March" is a question this gets asked, and a diff would make answering it a replay exercise.
- **The one-primary rule now lives in one function** (`assertExactlyOnePrimary` in `leads.validation.ts`) used by create, the general lead PATCH and the new contacts PATCH. It was previously inline in create only, which meant `PATCH /api/crm/leads/:id` accepted a contacts array with zero or two primaries — a way around a constraint create enforced. Same rule, all three doors. Verified: both bad shapes are now 400 on both routes.
- **Marking a lead dead is the LOST transition, not a separate endpoint.** `POST /:id/transition` now also accepts optional `competitor` and `reengageOn` alongside the already-required `reason`, stored on the lead beside `lostReason`. Both are optional even on LOST, because the mandatory reason is the floor and demanding a competitor name for a lead that simply went cold just gets "n/a" typed into it. They are ignored on any other target — verified that a normal advance carrying them leaves both null.
- **Parking is orthogonal to the stage and does not touch it.** A new `parked` sub-document (`isParked`, `reason`, `revisitDate`, `parkedFromStage`, `parkedAt`) with `POST /:id/park` and `POST /:id/unpark`, both audited. The SoW requires a parked lead to resume from where it was parked, and the cheapest way to guarantee that is to never move it: unparking is just clearing the sub-document. Modelling "parked" as a stage would have destroyed that position and forced a pseudo-state into `TRANSITION_MAP` that every stage can reach and return from — a flag pretending to be a lifecycle. `parkedFromStage` is recorded so the audit trail can answer "where was this when we shelved it" and so any drift is visible rather than silently overwritten.
- **Both park routes refuse the meaningless cases**: double-park and double-unpark return 409, and a WON or LOST lead cannot be parked at all (terminal stages derived from `TRANSITION_MAP`, not hardcoded). The `⋯` menu does not offer Park on a terminal lead, so that refusal is not reachable from the UI.
- **UI**: the Contacts card opens a `Modal` reusing the intake wizard's one-primary **radio** behaviour (choosing one clears the rest; removing the primary promotes the first survivor). The LOST confirmation grew the two optional fields beside its required reason. The `⋯` menu gained Park, switching to Unpark while parked, and a **"Parked · revisit &lt;date&gt;"** pill sits beside the stage badge — beside, not instead of, because that is exactly the relationship.
- **Automatic revisit surfacing was deferred at the time this was written** — see the My Day entry below, which closes it: My Day reads `parked.revisitDate` directly, so a parked lead now returns on its own in the right person's queue. Park and unpark themselves remain manual actions.

**Done: deal value, budget band, and the Lead Inbox's own two charts.** The gap between the live inbox and the richer version it was always meant to be — one missing field and two thin aggregations, not the start of the Reports module.

- **`lead.indicativeValuePaise`** — optional, nullable, integer paise (hard rule #1). What we think the deal is worth, known from enquiry onwards. `null` is not `0`: null means nobody has priced it and renders as an em dash, 0 asserts the deal is worthless. `optionalPaiseField()` was added beside `paiseField()` in `utils/http.ts` for exactly this shape — the existing helper is `required` with `default: 0` and would have turned every unpriced lead into a zero-value one. Accepted on create and update; the Zod schema rejects fractional and negative amounts outright rather than rounding, because a non-integer arriving here means the client's unit conversion is wrong.
- **`lead.qualification.budgetMinPaise` / `budgetMaxPaise`** — on the qualification sub-document, **not** the lead root, because the SoW ties budget to the Qualified stage: it is an output of screening and belongs with the scores, date and author that produced it. Either end alone is valid ("at least 5 crore"); an inverted band is rejected on both sides.
- **The intake form and qualify modal collect crore, not paise.** These deals run to crores and asking for 75000000 invites a misplaced zero. `croreToPaise` in `lib/formatters.ts` converts once, on submit — the one legitimate rounding boundary, the same one `rupeesToPaise` occupies — and the wizard shows a live `paiseToDisplay` preview so the entered figure is confirmed before it is saved.
- **`GET /crm/leads/summary` now takes the list's filters** and returns five figures with two deliberately different scopes. `unassigned`, `noFirstResponse` and `arrivedToday` stay **whole-collection** because each is a filter target in the segmented bar — narrowing them would make "Unassigned" describe its own subset and stop being a number to drive to zero. `indicativeValueTotalPaise` and `slowestDaysWaiting` are **filtered**, because they describe the rows on screen. `arrivedToday` and `slowestDaysWaiting` are computed server-side rather than from the returned page: with oldest-first paging at 25, today's arrivals sit on the *last* page and a client-side count would read 0 on any real dataset.
- **Two thin aggregations**: `GET /crm/leads/reports/source-mix` (counts by `leadSourceId` over a trailing 90 days, labels resolved from the master rows so an admin rename propagates) and `GET /crm/leads/reports/criteria-tally` (per-criterion assessed count and mean, **excluding score 0** exactly as `computeQualificationScore` does, so the chart and the scores it summarises cannot tell different stories). Driven by the criteria list rather than by what happens to have scores, so an unassessed criterion shows an honest empty bar instead of vanishing. **Stage-conversion, loss-analysis and geography breakdowns are deliberately not built** — they belong to the full CRM Reports feature; see MODULE_MAP.md.
- **`buildLeadFilter` was extracted** so the list and the summary translate filters identically. **Reference ids must be cast to `ObjectId` there**: `Model.find()` casts a filter through the schema, but `Model.aggregate()` does not, and a raw string in a `$match` against an ObjectId field silently matches nothing. Caught in verification — a source filter produced correct rows beside a total of ₹0. For the same reason `deletedAt: null` is now explicit on every `countDocuments` and `aggregate` here: the soft-delete plugin hooks `/^find/`, which neither of those is.
- **UI**: the inbox's two clickable stat cards became **five read-only cards** (Unassigned, No first response, In the inbox + summed value in crore, Slowest waiting, Arrived today) plus a **segmented radio bar** — Everything / Unassigned / Awaiting first response / Arrived today. These slices are mutually exclusive by nature, and a card that was both a number and a toggle modelled them as combinable. Stage and temperature stay in `FilterBar`: those genuinely do combine. A right-aligned **Value** column renders through `paiseToDisplay` with an em dash for null. Both charts use `BarChart`; `DonutMeter` is a single-value completion ring and could not show a per-category breakdown without changing its contract, which this pass did not do. Below five leads (or five scored) each panel states what is missing and when it fills in, rather than drawing a shape from three points.

**Done: splitting Activities from My Day, and the commitment-provenance work that made the split honest.** Before this pass, the Activity Log and the lead detail's "Next action" card were two partial views of the same idea, and neither was quite right: the Activity Log was a backward-looking record trying to also hint at what was owed, and there was no forward-looking, cross-lead queue at all. The governing decision here is that these are two different things — **Activities is the historical record of what was done; My Day is the queue of what is owed** — and the fix was to build My Day properly rather than push the Activity Log further toward being one.

- **Commitment provenance.** A lead's `nextAction`/`nextActionDate` could always be set two ways — at intake (`AddLeadWizard`, with nothing behind it) or by logging a follow-up (`createLeadActivity`) — but nothing recorded *which* had produced the current value. Three denormalised fields now ride on the lead (`nextActionSourceActivityId`, `nextActionPromisedAt`, `nextActionPromisedByUserId`), written inside the same transaction `createLeadActivity` already runs, so the commitment and its provenance can never disagree. A manual reschedule through the general `PATCH /api/crm/leads/:id` (not an activity) clears all three: a typed-in date is not "promised at follow-up N", and leaving the old provenance in place would credit an activity for a promise it never made.
- **The lead detail response is now `getLeadDetail`, not the raw `getLead` document** — a separate read path (every other caller of `getLead`, contacts/transitions/park/qualify, wants a live document to mutate, not a snapshot with derived fields bolted on). It adds `ageDays` (total lead age) beside the existing `daysInStage`, `activitiesLoggedCount` (so the UI can say "Log follow-up 4"), and `brokenPromiseCount` — the count of this lead's own activities whose `nextFollowUpDate` fell before the *next* activity's `occurredAt`, via a shared `classifyFollowUp()` also used per-row in the flat list below.
- **The flat activities endpoint (`GET /api/crm/activities`) was rewritten** from a bare `find().sort().limit()` — which silently truncated an audit-grade log at whatever the default limit happened to be — into a real paginated, filtered list: `type[]`, `parentType`, `loggedByUserId`, `dateFrom`/`dateTo`, `hasFollowUp`, `overdueFollowUp`, `leadId`, real `page`/`pageSize`/`total`, and a `summary` aggregate (logged this week, calls/visits/emails, follow-ups committed, promises overdue) scoped to the same filters as the rows. `companyName`/`leadCode` are denormalised onto each row server-side — the Activity Log page no longer resolves labels against a second unpaginated fetch through `useLeadLabels()`.
- **An outcome guardrail closes a real data-quality gap.** Free text alone had already let an Excel date serial ("43244") and a bare "120" into production `outcome` values. A short `outcomeCategory` pick-list is now required before `outcome` free text is accepted, enforced by the same `superRefine` pattern used elsewhere in this codebase.
- **`ActivityRail`** (`apps/web/src/components/ActivityRail.tsx`) is the shared timeline named as outstanding D3 work in DESIGN_SYSTEM.md/MODULE_MAP.md: date-group separators, per-type icons, a two-line clamp with an expand toggle, the committed-follow-up chip, and a kept/broken badge resolved from `followUpOutcome`. Built once, used by both the lead detail workspace's timeline and the rebuilt Activity Log — a formatting fix in one now reaches both, where before they were two hand-rolled lists.
- **The Activity Log page (`/app/crm/activities`) was rebuilt** on `ActivityRail` plus a real table view behind the existing `ViewToggle` (which gained optional `secondLabel`/`secondIcon` props so its "board" slot could be relabelled "Timeline" instead of "Kanban" without touching its other callers). A KPI strip, an Everything/Mine/This week/Visits-only segmented cut, `FilterBar` carrying a type select and a date range, and server-driven pagination replace the old scaffold. The `#` (per-lead `sequenceNo`) column is gone — it was meaningless across a cross-lead list, which is exactly why the page used to render 1, 3, 2, 1 down the column — and the number now lives in the lead cell as "follow-up 3". The subtitle no longer claims "newest sequence first"; the server sorts by `occurredAt`.
- **Lead detail workspace changes**: the header band now shows indicative value, lead source, and total age alongside stage/temperature/owner/days-in-stage. The "Next action" card moved from the bottom of the right rail to a **Commitment card** at the top, carrying the commitment text, due date, a red "Nd late" chip when overdue, the provenance line, and **Log follow-up N** / **Reschedule** actions (Reschedule opens a small modal over the general PATCH route — see the provenance-clearing note above). The stage rail now renders only the six stages a lead actually advances through; **WON and LOST render as terminal-exit chips branching off the rail** rather than steps 7 and 8 of one straight line, which used to imply LOST always follows WON. The qualification card no longer says "Not screened yet" on a lead already past QUALIFICATION — a lead that advanced unscored gets a quieter, retrospective message instead, with scoring still offered retroactively (chosen over gating stage advancement on screening, since that would change what moves are legal rather than just how the card reads). Contacts gained `tel:`/`mailto:` quick actions.
- **My Day (`/app/my-day`)** is the queue MODULE_MAP.md had listed as unbuilt. It reads three genuinely different "owed" signals side by side — `leads.nextActionDate`, a parked lead's `parked.revisitDate`, and a lost lead's `reengageOn` — and unifies them into one row shape with a `source` discriminant, since a lead can owe a follow-up for three different reasons that nothing before this queried together. A KPI strip (overdue follow-ups, due today, rest of this week, inbox needing action, completed today), three sections (Overdue / Today / This week) each headed with a count and the summed pipeline value in crore, and a Sales Head/Director team-view toggle that is advisory only — `GET /api/crm/my-day` re-derives `canAccess(role, crm, FULL)` server-side (exactly Director and Sales Head/BDE per §5's matrix) and downgrades `scope=team` to `mine` for anyone else, the same rule §6's seventh standing item states for every other hidden UI toggle in this app. This also closes the parked-lead automatic-revisit item noted above. When nothing is due, the page says so plainly rather than rendering three empty-looking tables — DESIGN_SYSTEM §6's rule against fabricated data covers a misleading absence of data as much as an invented number.
- **My Day sits above Dashboard in the sidebar, not inside the CRM nav section.** It is a hardcoded `Sidebar` link and a route declared directly in `router.tsx` (`/app/my-day`) rather than a `NAV_SECTIONS` entry — the same way Dashboard's own link works — because it is the screen the sales team opens every morning, and a CRM sub-item would put it a click below where it needs to be. The backend route stays under `/api/crm/my-day`: only the frontend's entry point moved, not which module owns the data.
- **Logging a follow-up or rescheduling now invalidates the My Day query too, from wherever either action is taken** — the Lead Detail Commitment card, the Lead Inbox's "Log first response," or My Day's own row actions. ## 1. Business context

Methanova Pvt Ltd is a BioCNG/CBG (Compressed Biogas) EPC (Engineering, Procurement, Construction) contractor. The company designs and builds biogas plants for clients, which means every deal is a long-running, capital-intensive engagement that moves through sales, statutory approvals, engineering, on-site execution, and finally ongoing plant operation. This system is the single system of record for that entire lifecycle: CRM for the sales motion, a compliance register for the regulatory approvals every plant legally requires before it can be built and operated, and a billing engine that matches Methanova's actual commercial terms (payment ahead of work, retention, mobilisation advances, GST).

The system must never let money, statutory status, or document versions drift out of sync with reality, because a mis-recorded GST split or a licence marked "granted" when it isn't has real regulatory and financial consequences.

## 2. The eleven-step lead-to-O&M process flow

1. **Lead enquiry** — a prospective client or site is logged as a Lead (organisation, contact, site location).
2. **Qualification** — Sales/BDE screens the lead for fit (feedstock availability, site viability, budget) before investing further effort.
3. **Site / plant visit** — a physical visit is logged as an Activity against the lead, informing feasibility and quotation.
4. **Quotation** — a priced proposal is issued. Quotations are **revision-controlled**: each revision points at its parent via `parentQuotationId`, so the full negotiation history of pricing is preserved rather than overwritten.
5. **Negotiation** — commercial terms are discussed and quotation revisions iterate until both sides agree.
6. **MOU (Memorandum of Understanding)** — a fee-bearing MOU is drafted and sent for signature. The MOU fee is the client's commitment payment.
7. **MOU signing → atomic spin-up** — the moment an MOU is marked SIGNED, the system atomically creates, in one database transaction: a **Project**, a **statutory site-feasibility survey** placeholder, a **licence/NOC checklist** (Pre-CTE, CTE, CTO), a **payment schedule**, and the **MOU-fee tax invoice**. This is the hinge point of the entire system — see §6, Rule 2.
8. **Statutory site-feasibility survey** — a formal survey (separate from the pre-MOU site visit) records statutory findings that feed the Detailed Project Report.
9. **Detailed Project Report (DPR)** — the engineering design document. It is **version-controlled**: each save is a new version, never an overwrite, so design history is auditable.
10. **Licence & NOC register + implementation schedule** — in parallel, the Liaison & Compliance Officer works the Pre-CTE/CTE/CTO licence bundle (each with an authority-visit log and a query/response log) while the Project Manager builds out the implementation schedule as an ordered list of **work packages** (a lightweight Gantt: sequence, planned start/end, value).
11. **Billing → commissioning → handover → recurring O&M** — as work packages complete, the billing engine raises a **proforma payment request** ahead of work, which converts to a **GST tax invoice** on receipt (with the correct CGST+SGST vs IGST split, retention withholding, and mobilisation-advance recovery netted off). Receipts are logged and receivables are aged. Once all work packages are done, the project is commissioned and handed over to the client, after which the same billing engine switches to **recurring Operations & Maintenance (O&M) invoicing**.

## 4. Lifecycle stage names (exact order — do not reorder or rename without updating `packages/shared-types/src/lifecycles.ts` and this document together)

**Lead stage** (`LeadStage`): `ENQUIRY → QUALIFICATION → SITE_VISIT → QUOTATION → NEGOTIATION → MOU → WON` (or `LOST` from any stage before WON).

> **"Parked" is not a stage and must never be added as one.** A parked lead is still at whatever stage it reached; it has simply gone quiet until its revisit date. It lives in the orthogonal `lead.parked` sub-document, and unparking restores nothing because nothing moved. Adding it here would destroy the position the SoW requires a parked lead to resume from, and would need a pseudo-state every stage can enter and return from — which is a flag, not a lifecycle.

**Licence status** (`LicenceStatus`): `NOT_STARTED → DRAFT → SUBMITTED → QUERY_PENDING ⇄ AUTHORITY_VISIT → GRANTED` (or `REJECTED`); `GRANTED → EXPIRED → DRAFT` (renewal loop).

**Invoice status** (`InvoiceStatus`): `DRAFT → PROFORMA_ISSUED → TAX_INVOICE_ISSUED → PARTIALLY_PAID → PAID`, with `OVERDUE`, `CANCELLED`, and `CREDITED` reachable as side branches per the transition map in `apps/api/src/core/state-machine/index.ts`.

**Work package status** (`WorkPackageStatus`): `PLANNED → READY → IN_PROGRESS ⇄ ON_HOLD → COMPLETED → HANDED_OVER`.

**MOU status** (`MouStatus`): `DRAFT → SENT → SIGNED` (or `CANCELLED`).

**Quotation status** (`QuotationStatus`): `DRAFT → PENDING_APPROVAL → APPROVED → SENT → UNDER_NEGOTIATION → ACCEPTED` (or `REJECTED` from `SENT`/`UNDER_NEGOTIATION`, or back to `DRAFT` from `PENDING_APPROVAL`). `SUPERSEDED` is reachable from every non-terminal state but is never offered as a manual transition — `createQuotation()` sets it as a side effect of creating a later revision against a quotation, the moment that revision is saved.

The full allowed-transition graph (including which jumps are illegal) lives in one place only: `packages/shared-types/src/transitions.ts`. It moved there from the API during D3 so the kanban boards can avoid offering moves the server would reject; `apps/api/src/core/state-machine/index.ts` imports it and keeps only the enforcement wrapper (`assertTransition`, which throws 409). Never hardcode a second copy of these graphs anywhere else.

## 5. Role-to-module permission matrix

Modules: `crm`, `projects`, `compliance`, `documents`, `schedule`, `billing`, `receivables`, `reports`, `admin`. Access levels: `NONE < READ < WRITE < FULL`. Canonical source: `packages/shared-types/src/permissions.ts` (`PERMISSION_MATRIX`, enforced server-side by `requirePermission()` in `apps/api/src/middlewares/index.ts`).

| Role | crm | projects | compliance | documents | schedule | billing | receivables | reports | admin |
|---|---|---|---|---|---|---|---|---|---|
| Director | FULL | FULL | FULL | FULL | FULL | FULL | FULL | FULL | FULL |
| Sales Head / BDE | FULL | READ | – | WRITE | – | – | – | READ | – |
| Liaison & Compliance Officer | – | READ | FULL | WRITE | – | – | – | READ | – |
| Design/Engineering Lead | – | WRITE | – | WRITE | READ | – | – | READ | – |
| Project Manager | READ | FULL | READ | WRITE | FULL | READ | – | READ | – |
| Site Engineer | – | READ | – | WRITE | WRITE | – | – | – | – |
| Accounts | READ | READ | – | – | – | FULL | FULL | READ | – |
| Client (external) | – | – | – | READ | READ | READ | – | – | – |

Notes:
- Blank cells are `NONE`, not an oversight — a role with no listed access to a module cannot even read it.
- `Client` is an external portal role: read-only, and only across the three modules a client should ever see (their documents, their schedule, their invoices).
- Changing this matrix is a product decision, not just a code change — update this table and `permissions.ts` together.

## 6. Engineering conventions (hard rules, not suggestions)

1. **Money is always an integer in paise.** Never store or compute a monetary value as a float or an unrounded decimal. Use `Paise` / `assertPaise` / `rupeesToPaise` / `paiseToDisplay` from `packages/shared-types/src/money.ts` and `paiseField()` / `applyBps()` from `apps/api/src/utils/http.ts` and `gst.ts`. A GST split that doesn't divide into whole paise is a bug, not something to round away silently — `applyBps` throws rather than rounding.
2. **MOU signing is one atomic transaction.** `signMou()` in `apps/api/src/modules/crm/mou/mou.service.ts` opens a single `mongoose` replica-set session and creates the Project, PaymentSchedule, Licence checklist, and MOU-fee Invoice inside `session.withTransaction(...)`. If any step fails, the entire spin-up rolls back — there is never a half-created project with no invoice, or an invoice with no project. This is why `MONGODB_URI` must always include `replicaSet` (enforced at boot in `apps/api/src/config/index.ts`).
3. **Every invoice, proforma, and credit-note number comes from the atomic counters collection.** `nextNumber()` / `nextSequence()` in `apps/api/src/core/counters/index.ts` use `findOneAndUpdate` with `upsert: true`, so numbering is gapless and gets allocated exactly once per document — including inside the MOU-sign transaction. A cancelled invoice keeps its number forever; numbers are never reused or decremented.
4. **Every status field moves through an explicit transition map, never a direct field write.** Lead stage, licence status, invoice status, and work-package status are all governed by `TRANSITION_MAP` in `apps/api/src/core/state-machine/index.ts`. Services call `assertTransition()` / `applyStatus()` — they do not do `doc.status = x` unchecked. If a new transition is legitimately needed, add it to the map (and to §4 above) rather than bypassing it.
5. **Every financial record change, status transition, and document action is logged to one polymorphic `audit_logs` collection.** This happens through the shared `auditPlugin` Mongoose plugin (`apps/api/src/db/plugins/audit.plugin.ts`, faced by `apps/api/src/core/audit/index.ts`), applied to every schema via `applyDomainPlugins()`. Use `applyActor(doc, actorId, action)` before saving so the entry records who did what.
6. **Soft deletes only — no hard deletes anywhere.** `softDeletePlugin` (`apps/api/src/db/plugins/soft-delete.plugin.ts`) adds `deletedAt`/`deletedBy`, filters every find query to exclude soft-deleted docs by default, blocks `deleteOne`/`deleteMany`/`findOneAndDelete` at the schema level (they throw), and exposes `doc.softDelete(actorId)` as the only sanctioned way to remove a record.

**Role-based access is a seventh standing rule enforced alongside these six**: every module route is gated server-side by `requirePermission(module, level)` reading the permission matrix in §5 — client-side hiding of a menu item is a UX nicety, never the actual access control.

## 7. Feature phasing (P1 / P2 / P3) — do not build out-of-phase work prematurely

**P1 — core deal lifecycle + billing spine (must exist for a pilot):**
- Auth, Users, Roles, Master Data, and the full RBAC permission matrix — **auth/session/app-shell is done; user create/edit/deactivate UI is done.** Remaining P1 master-data gaps are none for the screens that exist; GST rates stay a generic Master Data row.
- CRM: Leads, Activities, revision-controlled Quotations, MOU
- The atomic MOU-sign spin-up (Project + PaymentSchedule + Licence checklist + MOU-fee Invoice)
- Compliance: Licence & NOC register with status transitions and embedded visit/query logs
- Schedule: Work Packages (flat Gantt list) and Progress Updates
- Billing: Payment Schedules, Invoices (Proforma → Tax Invoice), correct CGST/SGST vs IGST split, retention and mobilisation-advance fields on the invoice record
- Receivables: Receipts recorded against invoices
- Documents: versioned file metadata and local storage — **letterhead upload/download is real; the documents module list is still a stub**
- All six engineering conventions in §6, end to end

**P2 — operational depth (needed before broad rollout):**
- Full Feasibility Survey and DPR authoring/approval workflows (beyond a flat version counter — review, sign-off, supersede)
- Structured licence authority-visit and query-log workflows with officer follow-ups
- A real Reports dashboard (the P1 reports module is a raw snapshot list, not analytics)
- Receivables ageing as a proper report/dashboard (the P1 UI ships only a per-row ageing badge)
- Notification delivery beyond in-app (email/SMS) — the in-app channel is real (see the notifications engine entry above), but `emailEnabled` stays `false` and no SMS channel exists
- Explicit commissioning/handover checklist and sign-off on the Project entity
- Manual O&M invoice creation against a handed-over project

**P3 — scale, automation, and nice-to-haves:**
- Background jobs already stubbed in `apps/api/src/jobs/index.ts`: automatic `OVERDUE` status marking for unpaid tax invoices, and computed receivables-ageing buckets
- Automated recurring O&M invoice generation on a schedule (P2 ships manual creation first)
- A dedicated Client-portal experience (the `CLIENT` role's read-only access is already modeled in §5, but no client-facing UI/theme exists yet)
- Advanced reporting/BI (exports, charts, trend analysis)
- E-signature integration for MOU and quotation sign-off
- Multi-currency or multi-GSTIN entity support
- SLA/escalation automation for licence queries
